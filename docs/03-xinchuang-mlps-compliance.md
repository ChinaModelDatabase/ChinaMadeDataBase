## 0. 文档定位（务必先读）

**本文档不是合规证明，也不是合规承诺。**

MDB 当前 14 个 crate 中 8 个为纯骨架（各 19 行，仅 crate 边界与 lint 约束）；
`mdb-storage` 仍为骨架，但 `mdb-wire`/`mdb-server` 已打通最小真实链路。本文档的实质内容是：

1. 梳理法规的**强制链条**，明确"不做会怎样"；
2. 给出**逐条差距分析**，标明每项当前状态；
3. 指出**若干项 MDB 自身无法解决、必须外购或对接的事项**。

### 0.1 最重要的一条结论

> **MDB 无法自行实现合规。**

《信息系统密码应用测评要求》规定：第三级信息系统的密码产品须达到 **GB/T 37092 二级及以上**。这意味着密码运算必须由**已取得商用密码认证的硬件密码模块（密码机/SDF/HSM）**承担。

MDB 的自研软件实现（`mdb-crypto` 中 SM3/SM4/SHA 等）**在密评中只能作为"非密码产品"的算法调用方，不能作为密码产品**。因此：

- MDB 的定位是**密码应用方案的使用者与集成者**，不是密码产品生产者；
- 密码机、SDF 服务、CA 证书体系**必须外购**；
- MDB 的工作是正确调用、并为测评提供证据。

任何"MDB 自研算法已满足密评"的表述都是错误的。

### 0.2 免责

本文档不构成法律意见，也不替代密码检测机构的评估结论。密评的最终判定权在第三方检测机构，且**必须由具备资质的机构实测**。文档中所有"状态"均为 MDB 团队的自我评估，不具备评估效力。

## 2. 法规强制链条

这部分决定了"不做会怎样"，是本文档优先级最高的内容。

```text
《密码法》第 27 条
   │  关基运营者应当使用商用密码保护，自行或委托开展密评
   │  密评应与等保测评相衔接，避免重复评估
   ▼
《商用密码应用安全性评估管理办法》
   │  第 6 条  重要系统须制定密评应用方案，同步规划/建设/运行，定期密评
   │  第 7 条  方案未通过密评，不得作为建设依据
   │  第 8 条  ★ 运行前必须通过密评；未通过不得投入运行
   │  第 9 条  ★ 运行后每年至少一次；未通过须整改
   ▼
《密码法》第 37 条 / 办法第 17 条
      罚款 10 万 ~ 100 万元；对直接责任人 1 万 ~ 10 万元
```

### 2.1 三个刚性时间点

| 阶段 | 强制要求 | 依据 |
|---|---|---|
| 规划 | 密评应用方案须先通过评估 | 办法第 7 条 |
| **上线前** | **必须通过密评，未通过不得投入运行** | 办法第 8 条 |
| **运行期** | **每年至少一次** | 办法第 9 条 |

**对 MDB 项目的直接含义：这不是"上线后补做的事"。没有前置的密码应用方案与合规设计，MDB 无法通过上线前的强制关卡。**

## 3. 合规目标定位

| 维度 | 目标 | 依据 |
|---|---|---|
| 等级保护 | 第三级（监督保护级） | 业务方定级，MDB 不自行决定 |
| 密评 | 第三级 | 与等保等级对应 |
| 密码产品安全等级 | **GB/T 37092 二级及以上** | 39784 通用测评要求 |
| 密码算法 | 国密算法（SM2/SM3/SM4） | 密码法 |

### 3.1 定级不是 MDB 的决定权

等保定级是**运营者**的责任，需公安机关备案。MDB 只能**假设**目标为三级并据此设计。**若实际定级为四级，密码产品安全等级要求将升至 GB/T 37092 三级，硬件与采购成本显著上升。**

这一条必须在项目启动时与甲方书面确认，写入密码应用方案。

## 4. 密码算法合规性对照

| 算法 | 标准 | MDB 状态 | 判定 |
|---|---|---|---|
| SM3 杂凑 | GB/T 32905 | `mdb-crypto/src/sm3.rs`（190 行） | 🟢 已实现 |
| SM4 分组密码 | GB/T 32907 | `mdb-crypto/src/sm4.rs`（300 行） | 🟡 块加密+CTR 已实现，**GCM 未实现** |
| SM4-CBC | GB/T 32907 | ⬜ 未实现 | TLCP 必需，见 §8 |
| SM4-GCM | 见 §7 说明 | ⬜ 未实现 | TDE 建议路径 |
| SM2 非对称 | GB/T 32918 | ⬜ **无软件实现** | 仅在 `hw.rs` 的 `Hsm` trait 上有 `sm2_sign`/`sm2_verify` |
| SM9 标识密码 | — | ⬜ 未实现 | 数据库场景一般不需要 |
| SHA-1/256、MD5 | 非国密 | ✅ 已实现 | 见 §4.1 |

### 4.1 重要区分：兼容用算法不能计入密评

`mdb-crypto` 已实现 SHA-1、SHA-256、MD5，这是**为了兼容 MongoDB 的 SCRAM/MD5 认证**（`net.tls.MONGODB-X509` 等）。

> **这些不是商用密码算法，在密评中不能作为受保护数据的保护手段。**

因此 MDB 的认证体系需**双轨**：

| 用途 | 算法 | 是否计入密评 |
|---|---|---|
| MongoDB 兼容认证 | SCRAM-SHA-256 / MD5 | ❌ 否 |
| 国密认证 | SM3 + SM2 口令认证 | ✅ 是 |

**不能因为实现了 SCRAM-SHA-256 就认为满足了密评的鉴别要求。**

### 4.2 SM2 缺失的影响面

SM2 缺失导致以下能力**全部不可用**：

- TLCP 握手与服务端身份认证
- X.509 证书中的 SM2 公钥验签
- SM2 密钥协商
- 报文签名的不可抵赖性

**这是 MDB 密码能力链上的最大断点**，且无法通过"补一个算法"解决——自研 SM2 同样不产生合规性（见 §0.1）。

## 5. 密码产品合规性（GB/T 37092 二级门槛）

### 5.1 门槛要求

| 信息系统密评等级 | 密码产品要求 |
|---|---|
| 第一级 | 符合法律法规相关要求 |
| 第二级 | GB/T 37092 一级及以上 |
| **第三级** | **GB/T 37092 二级及以上** |
| 第四级 | GB/T 37092 三级及以上 |
| 第五级 | 符合法律法规相关要求，依法需认证的应已认证 |

### 5.2 MDB 现状与结论

`mdb-crypto/src/hw.rs` 的架构方向是**正确的**：

```rust
pub trait Hsm: std::fmt::Debug + Send + Sync {
    fn gen_data_key(&self, len: usize) -> Result<DataKey, HsmError>;
    fn wrap_dek(&self, kek: &MasterKey, dek: &DataKey) -> Result<Vec<u8>, HsmError>;
    fn sm2_sign(&self, key_id: &[u8], data: &[u8]) -> Result<Vec<u8>, HsmError>;
    fn sm4_gcm_encrypt(&self, key: &[u8; 16], iv: &[u8; 12], aad: &[u8], pt: &[u8]) -> ...;
}
```

`Hsm` trait + `SoftwareHsm` + `install(Box<dyn Hsm>)` 的设计，**已经把硬件密码机抽象为 trait**，这是与认证密码机对接的正确姿势。

**但结论必须说清楚：**

| 组件 | 能否满足三级密评 |
|---|---|
| `Hsm` trait 接口设计 | ✅ 设计正确 |
| `SoftwareHsm`（软件模拟） | ❌ **不能**。自研软件不构成 GB/T 37092 密码产品 |
| 真实 SDF/HSM 对接 | ⛔ **未实现**（无 TCP/PCIe 传输代码） |

> `hw.rs` 中 `allow_software_fallback` 默认关闭的设计是**正确且必要的**：它防止系统在没有真实密码机的情况下"看起来在用密码设备"。这个开关在合规部署中必须保持关闭。

### 5.3 必须外购的组件

| 组件 | 要求 | 备注 |
|---|---|---|
| 硬件密码机 / SDF 服务 | GB/T 37092 二级及以上，取得商用密码认证 | **MDB 不能自研替代** |
| CA / 证书服务 | 签发 SM2 证书 | 用于 TLCP |
| 密钥管理 | 密钥生成、导入、分发、销毁的合规流程 | 制度 + 工具 |
| 完整性保护 | CRC32C（`mdb-crypto/src/crc32c.rs`，已实现） | 非密码算法，不计入密评 |

## 7. 存储加密（TDE）差距

### 7.1 SM4-GCM 存在一个规范问题

**注意：商用密码标准中并没有 SM4-GCM 的正式标准文本。**

SM4（GB/T 32907）定义的是分组密码；GCM 是 NIST 的 AEAD 模式，SM4-GCM 属于**行业实践组合**，而非国家标准规定的算法。

这对密评有实际影响：**测评机构可能不接受 SM4-GCM 作为合规的认证加密手段。** 需要在方案阶段与检测机构确认，或采用以下替代：

| 方案 | 加密 | 完整性 | 合规性 |
|---|---|---|---|
| SM4-CBC + HMAC-SM3 | CBC | 独立 MAC | 机制明确，但需防 CBC 组合攻击（Encrypt-then-MAC） |
| SM4-CTR + HMAC-SM3 | CTR | 独立 MAC | CTR 无需填充，MAC 独立，组合较安全 |
| SM4-GCM | GCM 内置 | GCM 内置 | 实践主流，但**标准依据需确认** |

> `sm4.rs` 现有注释已经暴露了这个问题的存在："**不得**用软件 CTR 替代硬件 GCM 通过密评"——即当前设计假定 GCM 由硬件提供。这个假定同样需要与检测机构确认。

**这是一个必须在方案阶段澄清、且可能推翻 TDE 设计的合规风险。不应留到实现阶段才发现。**

### 7.2 `docs/02` 的 TDE 设计需据此复核

`docs/02` §9 采用"块级 SM4-GCM"。**在 §7.1 结论确定前，该设计应视为待定**。若检测机构不接受 SM4-GCM，需改为 CBC/CTR + 独立 MAC，届时：

- 每块需额外存储 MAC 字段
- CRC32C 的角色从"完整性保护"降为"偶发错误检测"（二者不可互相替代：CRC 防位翻转，MAC 防篡改）

## 8. 传输层 TLCP 差距

### 8.1 TLCP 的实际情况

GB/T 38636-2020 基于 GM/T 0024-2014（SSL VPN 技术规范），其记录层沿用 **TLS 1.1 结构**：

| 项 | TLCP 实际取值 |
|---|---|
| 协议版本号 | `major=1, minor=1`（TLS 1.1） |
| 记录层分组 | ≤ 2^14 字节 |
| 主体加密 | SM4-CBC（`enum{sm4}` + `enum{block}`） |
| MAC 算法 | SM3 或 SHA-256（`HMAC_hash(MAC_write_secret, seq_num ‖ type ‖ version ‖ length ‖ fragment)`） |
| 主密钥长度 | 48 字节 `master_secret` |
| 随机数 | `client_random` / `server_random` 各 32 字节 |
| 序列号 | `uint64`，**不可回退**，溢出须重新握手 |

> **TLCP 不使用 GCM。** 传输层是 CBC + 独立 MAC，与 §7 存储层是两条不同的技术路线，不可互相套用结论。

### 8.2 MDB 现状

**`mdb-crypto` 中不存在任何 TLS 或 TLCP 代码。** 已确认无 X.509 / DER / PEM 解析模块，无握手实现，无记录层。

`AuthMode::X509` 在 `config.rs:83` 存在，但同样只是配置枚举，没有证书校验实现。

### 8.3 差距规模评估

| 工作项 | 规模 | 说明 |
|---|---|---|
| X.509 / DER / ASN.1 解析 | 大 | 零依赖自研，SAN 扩展、SM2 OID 等 |
| SM2 签名/验签软件实现 | 中 | 但见 §0.1，自研无合规性 |
| TLCP 握手（基于 TLS 1.1） | 大 | 状态机、密钥协商、证书链验证 |
| TLCP 记录层 + SM4-CBC + HMAC-SM3 | 中 | 算法侧已有 SM3/SM4 块加密 |
| 双协议栈（TLS 1.2/1.3 + TLCP）并存 | 很大 | MongoDB 驱动兼容性要求 |

**建议：不要自研传输层。** 见 §11 采购清单。

## 9. 密钥体系设计

### 9.1 分层（对应 `hw.rs` 现有结构）

| 层级 | 密钥 | 算法 | 存储位置 | 当前状态 |
|---|---|---|---|---|
| 根 | 主密钥 MEK | SM4 / SM2 | **仅在密码机内** | ⬜ |
| 中 | 密钥加密密钥 KEK | SM4 | 密码机内 | ⬜ |
| 数据 | 数据密钥 DEK | SM4 | 密码机内 + 包装后落盘 | 🟡 接口已有 |
| 证书 | SM2 证书 | SM2 | 文件 + 密码机私钥 | ⬜ |

`hw.rs` 已有 `MasterKey` / `DataKey` 分层与 `wrap_dek`/`unwrap_dek`，**结构与合规要求一致**。

### 9.2 关键合规要求

| 要求 | 说明 |
|---|---|
| 密钥不落盘 | MEK 永不写入任何文件、日志、`MANIFEST` |
| 密钥全生命周期 | 生成→分发→使用→备份→销毁，每阶段均需制度与记录 |
| 密钥与数据分离 | 密钥不得与被保护数据同库同目录 |
| 身份唯一 | 每 DEK 有唯一标识，绑定 CF 与轮换代次（`docs/02` §9.3） |
| 无残留 | 内存中的密钥需在使用后清零（见 §6.3 剩余信息保护） |

### 9.3 剩余信息保护的具体要求

`forbid(unsafe_code)` 限制下**无法保证编译器不清零内存**。Rust 的 `Vec<u8>` drop 时不保证擦除。

合规做法：**优先在密码机内部完成密钥运算**，减少密钥在 MDB 进程内的驻留。若必须驻留，需：

- 使用显式清零的包装类型（Drop 时覆写）
- 避免 `clone`、`to_vec` 产生额外副本
- 避免 `format!`/`Debug` 打印密钥（`MasterKey` 需检查是否派生了 `Debug`）

> ⚠️ **已核实的接口缺陷（G12）**：`hw.rs` 中
> ```rust
> #[derive(Debug, Clone, PartialEq, Eq)]
> pub struct MasterKey(pub Vec<u8>);
> ```
> 同时具备**两个**密钥泄漏途径：
> 1. 派生了 `Debug` → 任何 `{:?}`、`dbg!`、或 `Result` 的 panic 消息都会**直接打印主密钥明文字节**；
> 2. 元组字段为 `pub` → 任何持有者可直接读取密钥字节。
>
> `DataKey` 有同样问题。这不是"理论上可能"，而是当前代码的既成事实，**实现前必须修正**（去掉 `Debug`/`Clone`，字段改为私有并提供显式清零的 `Drop`）。

## 10. 差距汇总

| # | 差距项 | 等级 | 严重度 | MDB 能否自解决 |
|---|---|---|---|---|
| G1 | 无任何 TLS/TLCP 实现 | 三级必需 | 🔴 阻断上线 | ❌ 应外购 |
| G2 | SM2 无软件实现 | 三级必需 | 🔴 阻断上线 | ⚠️ 可实现但无合规性 |
| G3 | 无 X.509/DER/PEM 解析 | 三级必需 | 🔴 阻断上线 | ⚠️ 可实现 |
| G4 | 无 SDF/HSM 对接（无 TCP/PCIe 传输） | 三级必需 | 🔴 阻断上线 | ✅ 可实现 |
| G5 | `SoftwareHsm` 不能满足 37092 二级 | 三级必需 | 🔴 阻断上线 | ❌ **必须外购密码机** |
| G6 | 无 TDE | 三级必需 | 🔴 阻断上线 | ✅ 可实现 |
| G7 | ~~CRC32C 未实现~~ **已实现**（`mdb-crypto/src/crc32c.rs`） | 三级必需 | ✅ 已关闭 | ✅ |
| G8 | SM4-GCM 标准依据存疑 | 需确认 | 🟠 高 | ❌ 需检测机构裁定 |
| G9 | 无审计模块 | 三级必需 | 🟠 高 | ✅ 可实现 |
| G10 | 剩余信息保护缺失 | 三级必需 | 🟠 高 | ✅ 可实现 |
| G11 | 国密认证体系缺失（仅有 SCRAM） | 三级必需 | 🟡 中 | ⚠️ 部分 |
| G12 | `MasterKey` 可被 `Debug` 泄漏 | 通用要求 | 🟡 中 | ✅ 可实现 |
| G13 | `use_sm_cipher` 是空承诺字段 | — | 🟡 中 | ✅ 可实现 |
| G14 | 无密码应用方案（业务侧） | 前置条件 | 🔴 阻断上线 | ❌ 甲方责任 |

**阻断上线的共 7 项（🔴），其中 4 项 MDB 无法自行解决。**

## 12. 实施建议顺序

密评有强时序约束，**顺序错误会导致方案返工**：

```text
第 0 步  甲方定级 + 编写密码应用方案 ──────►  提交检测机构评审（办法第 7 条）
              │                                        │
              │ 方案确定后                              │ 方案通过
              ▼                                        ▼
第 1 步  密码机/证书选型定型（P1/P2）            启动正式建设
第 2 步  SDF/HSM 对接（G4）+ 修正密钥接口（G12）
第 3 步  TDE + 完整性保护（G6/G7/G10）
第 4 步  传输层（外购或对接 G1/G2/G3）
第 5 步  审计 + 国密认证（G9/G11）
              │
              ▼
第 6 步  上线前密评（办法第 8 条）── 未通过不得投入运行
第 7 步  运行后每年密评（办法第 9 条）
```

**第 0 步不在 MDB 控制范围内，必须最先启动。** 在密码应用方案评审通过前投入 TDE/传输层开发，存在整体重做的风险。
